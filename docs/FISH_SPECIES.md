# 魚種データと画像（Phase 4C-1B）

`src/game/fish-species.js` は描画・DOMに依存しない魚種定義です。
魚の一般的な体型・模様・食性を参考にした通常魚の説明と、**ゲーム用の暫定バランス値**を持ちます。
体長範囲はゲームに登場させる個体の範囲で、実在魚の最小・最大記録ではありません。
重量係数、抵抗力、価格も生物学的な実測値や市場価格ではありません。

## 取得と互換性

- `FISH_SPECIES`：仕様書の12種を固定順で並べた読み取り専用配列。
- `getFishSpecies(id)`：ID検索。未登録IDは `undefined`（別魚種への自動置換なし）。
- `BLACK_BASS`：従来の `black-bass`、表示名「ブラックバス」、25〜55cmを維持。
  別名 `alternateName` は「ラージマウスバス」。`fishing-config.js` からの既存importも再exportで維持。
- `calculateFishWeightKg(id, lengthCm)`：体長から重量を計算。未登録ID、非数値、魚種の範囲外の体長は `RangeError`。
- 定義・重量係数・ファイト係数はfreeze済み。登録時に必須項目とID重複を検証する。
  既存のIDと配列順は将来の釣果・図鑑の参照用として安定させる。

## 単位・計算式

体長はcm、重量はkg。`weight` は基準体長 `referenceLengthCm`、基準重量 `referenceWeightKg`、指数 `exponent` を持ちます。

```text
重量kg = referenceWeightKg × (体長cm / referenceLengthCm) ^ exponent
```

小数第2位まで丸めます。ブラックバスは従来どおり `1.1 × (体長 / 40)^3` です。
現在の全魚種の指数は3で、必要に応じて魚種別に変更できます。

`fight` の `baseResistance` は無次元の基本抵抗力、`lengthScaleCm` は体長による増加の尺度、
`surgeAmplitude` は引きの変動幅、`surgeFrequency` は角周波数（rad/秒）、`style` は特性の説明です。

```text
抵抗 = baseResistance + (体長cm - 最小体長cm) / lengthScaleCm
       + surgeAmplitude × sin(ファイト経過秒 × surgeFrequency)
```

ブラックバスの係数はPhase 2の `0.85 / 100 / 0.15 / 2.4` をそのまま移しています。
Phase 3A-2では全12種の係数を実際のファイトに適用します。巻き取り速度には共通の抵抗下限・上限を設け、初期装備でも捕獲できるようにしています。
抽選・ルアー適性・ファイト時間の調整箇所は [釣りバランス](FISHING_BALANCE.md) を参照してください。
`style` の文章による挙動分岐や、ジャンプ・魚の3Dアニメーションは実装していません。

`basePricePerKg` はゲーム内通貨/kgの基準単価です。[Phase 3B-2](FISH_SALES.md)の価格関数が「魚種別基本価格 × 重量」を計算し、売却時の通貨付与に使用します。暫定単価は変更していません。

## 通常魚の画像

12種ともBARB用にAI生成し、個別に形態を確認した自然史図鑑風の透過PNGです。
右向きの全身側面図、1280×560px、RGBA8、非インターレース、sRGBで統一しています。
ブラックバスを含め `src/assets/fish/<species-id>.png` に配置します。外部画像の転載や有料素材は使用していません。
制作方法・プロンプト・形態資料・利用条件・品質レポートは[画像制作記録](FISH_ARTWORK.md)を参照してください。
魚種定義の `image` は静的な `new URL(..., import.meta.url)` による参照で、Viteのビルドと `/barb/` 配信に対応します。
将来の差し替えもローカルSVG／透過PNGを使用できます。描画コード・捕獲データの変更は不要です。
未発見魚の共通シルエット `unknown.svg` は維持しています。

## 登録データと将来の追加手順

`fish-species.js` の既存の配列へ定義を記述する方式を維持しています。
`fish-species-registry.js` の `defineFishSpecies()` がメタデータを検証・コピー・freezeし、
`createFishSpeciesRegistry()` が重複IDを拒否します。これは構築用の関数で、本番のリストへ
実行中に追加するAPIではありません。レジストリの検索も未知IDは `undefined` です。

| 項目 | 必須条件・用途 |
| --- | --- |
| `id` | 一意で固定の小文字英数字・ハイフン（先頭は英字）。保存・抽選・図鑑の参照キー |
| `name`, `description` | 空でない表示名・説明 |
| `alternateName` | 任意。指定時は空でない別名 |
| `minLengthCm`, `maxLengthCm` | 正の有限値、最小＜最大 |
| `weight` | 正の有限値の `referenceLengthCm`, `referenceWeightKg`, `exponent`。基準体長は範囲内 |
| `fight` | 正の有限値の `baseResistance`, `lengthScaleCm`, `surgeAmplitude`, `surgeFrequency` と空でない `style`。振幅＜基本抵抗力 |
| `basePricePerKg` | 正の安全な整数の基準単価 |
| `image` | 空でない参照文字列。下記の静的なローカルURLを使い、ファイル内容は別途検証 |

将来、新魚種を追加する場合：

1. 既存のID・日本語名・別名・数値・配列順を維持して末尾へ新しい定義を追加する。既存IDの流用や、削除した魚への自動置換をしない。
2. 出典・ライセンスを確認したローカル画像と、すべての登録項目を用意する。出典・利用条件が不明の素材を本番へ取り込まない。
3. `APPEARANCE_WEIGHTS`、各ルアーの `affinities`、水深・時間帯補正をレビューする。未登録キーの既定値はそれぞれ1（中立）。既定値でも抽選できるが、他種の正規化後の確率も変わるので追加のバランス判断が必要。
4. 図鑑の追加枠・表示順、実績条件、保存互換性を別途決定する。「5種発見」「全12種発見」は現在5・12の固定条件であり、魚種総数へ自動連動させない。
5. 登録・画像・抽選・ファイト・価格・保存・UIのテストを追加し、P3-Bの分類に従って検証する。

今回は一時的にコピーしたモジュールだけへ仮魚種を追加し、中立の抽選・ルアー・環境補正と価格参照をテストします。本番には登録しません。

## SVG／透過PNGの確定した対応条件

参照は各定義にリテラルで記述します。

```js
image: new URL('../assets/fish/example.png', import.meta.url).href,
```

`.svg` も同様です。パスを変数から動的に連結するローダーや外部URLは使用しません。
Viteが本番アセットをハッシュ付きの `/barb/assets/…` へ出力し、小さい画像はdata URLへ
インライン化する場合があります。どちらもローカルファイル由来です。
E2Eでは一時コピーの静的PNG参照を実際にViteでビルドし、出力ファイルとインライン画像を
ブラウザで読み込みます。テスト用PNGや仮魚種を通常の本番ビルドへ混入させません。

`scripts/lib/fish-image-validation.js` を単体テストから使い、拡張子と内容を形式別に検証します。
本番魚種の参照はNode上で `file:` であることと実ファイルの存在も検証します。
実行時に画像をデコードしたり、画像情報をゲーム状態へ追加したりはしません。

| 形式 | 検証内容 |
| --- | --- |
| SVG | SVG名前空間・ルート・閉じタグ、有効な正のviewBox、従来の10,000 bytes未満。script、foreignObject、href/src、イベント属性等を拒否。内部の `url(#id)` は維持し、外部リソース・エンティティ・埋め込み要素等も拒否 |
| PNG | 署名、IHDR／IDAT／IENDの長さ・順序、全chunkのCRC、PLTE／tRNSの整合性、zlib展開長・行フィルター・パレット添字。RGBA／グレー＋alpha、または有効なtRNSを要求 |

PNGは非インターレースの静止画に対応します。ビット深度はPNGの組合せに従い、グレー1/2/4/8/16、RGB8/16、パレット1/2/4/8、グレー＋alpha8/16、RGBA8/16です。
RGBA等のalphaチャンネルは形式上の透過対応として受理します。すべてのピクセルが透けることを要求するものではありません。
APNG、未知のcritical chunk、透過情報のないRGB／グレー／パレット、破損・切断・余分なデータ、不明な拡張子、形式偽装は拒否します。
リソース上限はファイル8 MiB、各辺8192 px、総画素16 Mi、展開64 MiBです。これは異常入力の防止用で、制作時の推奨寸法ではありません。
SVG検証はリポジトリの信頼済み素材用の静的チェックであり、任意のアップロードSVGを安全化するサニタイザーではありません。

`tests/fixtures/fish-assets/transparent-test.png` は独自生成した40×64のテスト模様です。
透明・半透明・不透明の列を持ち、実素材・制作仕様の見本ではありません。

## 表示と保存の関係

釣果、発見済み図鑑一覧、図鑑詳細、保管一覧は魚種定義の `image` を使用します。
共通の `.fish-image-frame` が従来の背景色と表示領域を確保し、画像は背景を持たず
`object-fit: contain` で全体を収めます。画像自体の縦横比を保ち、読み込み前後の枠サイズを固定します。
枠の640:280は既存UIを保つための表示比率で、素材の寸法制約ではありません。
低い横画面の釣果枠は従来同様に100pxへ収めます。代替テキストは魚種名（釣果は側面イラスト）です。
未発見枠には共通シルエットと「？？？」だけを出力し、個別の名前・説明・画像URLをDOMへ入れません。

捕獲履歴は `speciesId` を持ち、画像URL・形式・寸法を保存しません。
図鑑統計と保管一覧は履歴から再構築し、売却価格は現在の魚種の単価から計算します。
画像参照だけの変更は抽選、重量、ファイト、価格、実績、セーブv1・2スロットの保存／復元へ影響しません。
新魚種を含むセーブを旧版で開く場合は未知IDとして厳格検証で拒否されるため、将来の追加時には
前方互換・実績仕様を改めて判断してください。今回は未知ID拒否と保存失敗時の保護・復旧を維持します。

## Phase 4C-1Bの制作仕様

本番12点は1280×560px、各800KiB以下、合計8MiB以下。輪郭外の透明背景と余白を検証します。
魚種ごとの体型を保って比例縮小・透明余白追加を行い、ヒレ・尾・ひげを切りません。
これは本番アートの納品仕様であり、SVG／PNG汎用バリデーターの許容寸法を狭めるものではありません。

## 検証とCI

```bash
npm ci
npm test
npm run build
npx playwright test tests/browser/fish-assets.spec.js tests/browser/save-data.spec.js --reporter=line
npx playwright test tests/browser/smoke-pc.spec.js tests/browser/smoke-touch.spec.js --reporter=line
```

単体テストは既存12ID・順序、登録必須項目・重複拒否、未知ID、両画像形式・破損拒否、
main `51ab225` の画像以外の全魚種・抽選・ルアー・環境補正・実績定義の互換性を検証します。
隔離したモジュールで仮魚種の中立値と、PNG差し替え後の旧v1捕獲履歴・図鑑・保管・売却・実績・抽選の不変性も検証します。
E2Eは共通診断fixtureと既存UI fixtureを使い、PC・タッチ縦横の4表示面、未発見情報のマスク、
読み込み前後の枠、透明／半透明の実画面合成、旧セーブ復元、Viteの `/barb/` URLを確認します。
既存の釣果E2Eも画像内容の照合を維持しながらSVG／PNG別の比較へ対応しています。

共有ゲームデータ・UI・共通fixtureの変更を含むため、P3-BではL2の全件E2Eを想定します。
実際の分類、全件の収集・実行、最新HEADの `ci-required` と統合状態はPMがActionsで確認します。
Codexは関連E2Eだけを局所実行し、全件はGitHub Actionsへ委任します。CI完了待機・継続ポーリング・マージは行いません。
