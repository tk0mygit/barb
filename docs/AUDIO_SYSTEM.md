# BGM・自然音（Phase 4B-2／4B-1,2 Update）

静かな湖の操作と釣りに集中できる、控えめな仮音源です。初期設定はOFFです。
「≡」→「サウンド設定」で **BGM・自然音** をONにし、0〜100%の整数で音量を調整します（初期音量40%）。
アタリ通知音は別系統で、環境音OFF／音量0でも従来どおりです。
メニュー内では環境音を一時停止し、閉じると現在の共有時計に従って再開します。
画面には現在の環境・停止／操作待ち／開始処理中／再生拒否／中断・設定保存の結果を表示します。

## 時計とミックス

| モード | 音源 | 判定 |
| --- | --- | --- |
| DAY | 穏やかな中低音の短いフレーズと柔らかな和音＋控えめな自然音 | 共有時計の昼 |
| NIGHT_CLEAR | 低い音域、少ない発音と余白のある別フレーズ＋控えめな自然音 | 霧のない夜 |
| NIGHT_FOG | CLEARと同じ夜BGMと自然音を維持 | 通常霧FOG（30〜70%） |
| NIGHT_DENSE_FOG | 風、水の揺れ、遠い鳥の声を参考にした控えめな合成自然音 | 濃霧DENSE_FOG（95%） |

`src/audio/audio-mix.js`の`sampleAudioMix(gameClock.state, target?)`はWeb Audio・DOMに依存しない絶対値計算です。
既存の`createGameClock()`（昼180秒、夜180秒）だけを参照します。夜霧の判定を複製しません。
自然音は独立レイヤーとして常時重ね、通常時のgainを`NATURE_BASE_GAIN = 0.25`とします。
`sampleNightFog()`がDENSE_FOGの場合だけ、BGMへ`1 - intensity`を掛け、
自然音を`0.25 + 0.75 * intensity`へ増やします。通常時のBGM音量は減らしません。
濃霧の前後12秒は描画と同じsmoothstepです。最大時はBGMが0、自然音だけになります。
通常のFOGは実効霧量やフェードにかかわらずCLEARと同じ夜BGMを維持します。
霧量0.95そのものを音量比にしないため、濃霧ピークでBGMが5%残ることはありません。
昼夜BGMは境界の前後8秒ずつでsmoothstepクロスフェードし、180／360秒で音量が飛びません。
モード名は共有時計の昼夜判定に従い、境界付近は両方のBGMが混ざります。
再読み込みでは保存された時計を最初から参照し、別タイマーや壁時計の経過分を使いません。

### 常時自然音の測定と数値保証（Phase 4.5-D-1）

既存の24秒PCM（mono、22,050Hz）を全サンプル測定しました。PCM、master最大0.3、
既定音量40%、通知音の音程・gain・経路は変更していません。

| 測定項目 | 昼BGM | 夜BGM（CLEAR／FOG） | 自然音 |
| --- | --- | --- | --- |
| 生PCM RMS | 0.03130547 | 0.02641287 | 0.02183912 |
| 生PCM peak | 0.09795384 | 0.09504970 | 0.11675113 |
| 通常環境のchannel gain | 1 | 1 | 0.25 |

自然音を0.25倍にするとRMSは0.00545978となり、昼BGMより15.17dB、夜BGMより13.69dB低くなります。
控えめな追加レイヤーの初期値として選び、BGMを維持した24秒全体の合成RMS増加を0〜0.2dBに制限します。
このRMS比は周波数による聴感や端末の聞こえ方を保証せず、デプロイ後のユーザー聴取で確認します。

| 状態（ゲーム経過秒の例） | 昼gain | 夜gain | 自然音gain：従来 → 今回 | 今回のgain合計 |
| --- | --- | --- | --- | --- |
| 昼（90） | 1 | 0 | 0 → 0.25 | 1.25 |
| 通常夜（270）／通常霧（2790） | 0 | 1 | 0 → 0.25 | 1.25 |
| 昼夜境界（180／360） | 0.5 | 0.5 | 0 → 0.25 | 1.25 |
| 濃霧開始（900）／終了（1080） | 0.5 | 0.5 | 0 → 0.25 | 1.25 |
| 濃霧フェード中間（906／1074） | 0.021484375 | 0.478515625 | 0.5 → 0.625 | 1.125 |
| 濃霧ピーク（912〜1068） | 0 | 0 | 1 → 1 | 1 |

gain合計1の正規化は行いません。代わりに、各PCMの絶対peakを`Pd`、`Pn`、`Pa`とすると、
任意のループ位相・昼夜／濃霧の目標ミックスに対する音量100%の出力上限は
`0.3 * max(max(Pd, Pn) + 0.25 * Pa, Pa) = 0.03814249`です。
この上限は0.04未満（約−28.37dBFS）で、通知音1回のpeak 0.12を加えた上限も0.15814249、0.16未満です。
急な時計ジャンプや連続再設定では、3つのgainが80msランプの異なる位置にある可能性も考慮します。
各gainが0〜1に収まることから、その場合も保守的な上限は`0.3 * (Pd + Pn + Pa) = 0.09292640`、
0.1未満です。通知音1回を加えても0.21292640、0.22未満で、デジタルクリップの1を十分下回ります。
単体テストはこれらの位相非依存の上限とRMS差を検証します。保証は現行PCMと現行masterに対するもので、
端末の音量増幅や出力機器での歪みを測定した値ではありません。

ネイティブOfflineAudioContextでも実PCMを音量100%で4環境・夕暮れ・夜明け・濃霧開始／終了へ通し、
有限値、クリップサンプル0、peak 0.04未満、最大隣接サンプル差0.0061未満を検証します。
一定値PCMによる30／60／144fps・不規則更新の検証は、通常時の出力を
`0.3 * 0.4 * 1.25 = 0.15`として、従来の誤差と段差のしきい値を維持します。
Chromium 154.0.8037.57での実測最大peakは0.03502535、最大隣接サンプル差は0.00598692、
クリップサンプルは0でした。一定値PCMの8条件は0.14999987〜0.15000013、
最大隣接サンプル差0.00016992、停止完了後は厳密に0でした。

`render-audio-preview.mjs`で新旧それぞれ10本を生成した比較では、既定音量40%のRMS増加は
昼+0.1164dB、通常夜+0.1739dB、通常霧+0.1736dB、夕暮れ+0.1679dB、夜明け+0.1771dB、
濃霧開始+0.2638dB、濃霧終了+0.2535dB、濃霧ピークは0dBでした。
0.2dBの保証は通常環境の24秒全体RMSに対するもので、移行区間の新旧差へは適用しません。
いずれも正規化していないPCM解析であり、聴取評価は未完了です。

## 責務と音源の交換

| ファイル | 責務 |
| --- | --- |
| `src/audio/audio-mix.js` | 時計と霧からモード・3音源の目標比率を計算 |
| `src/audio/audio-session.js` | ユーザー操作による共有AudioContextの初回生成・resume・状態通知・close |
| `src/audio/generated-sources.js` | 音源生成factory。将来OGG／MP3等をデコードしたAudioBufferへ交換する境界 |
| `src/audio/ambient-player.js` | ループ音源管理、独立gain、80msの開始／停止・音量変更、解放 |
| `src/audio/ambient-audio.js` | 設定、停止理由の合成、再生状態、純粋ミックスとplayerの接続 |
| `src/audio/audio-preferences.js` | 小規模なユーザー設定専用の厳格検証・読み書き |
| `src/ui/sound-settings.js` | DOM操作と状態表示。音声エラーをゲームの保存状態へ流さない |
| `src/ui/fishing-audio.js` | 従来のアタリ音。環境音masterを通さない独立gain |
| `src/main.js` | 共有時計、ユーザー入力、メニュー、ページのライフサイクルを接続 |

各音源は24秒・mono・22,050Hzの固定PCMループです。昼夜は正弦波と弱い倍音、滑らかな音符エンベロープ、
自然音は固定seedの帯域を抑えたノイズ、緩い振幅変化と短い丸い音を合成します。
継ぎ目も連続させます。強い打楽器、ホラー旋律、驚かせる音は追加しません。
コード内の音列・合成式をこのプロジェクト用に作成し、既存曲・録音・外部サービス・不明なライセンスの素材を使用していません。
生成コードと出力は本リポジトリのライセンス方針に従います。第三者素材を導入する場合は別途出典と利用条件を記録してください。

生成は再生が必要になった時だけで、3本合計約6.1MiBのPCMをキャッシュします。
1つのbank（ループsource 3個、channel gain 3個、master gain 1個）だけを管理します。
通常更新でノードやPCMを生成せず、異なる目標値へだけgainを滑らかに動かします。
環境音masterは最大0.3倍、音源peakも抑えており、既存アタリ音のpeak 0.12を保ちます。
数値上の差は聴感上の聞き取りやすさの保証ではありません。
停止は80msフェードの後にsourceをstop／disconnectし、参照を解除します。
停止直後の再開は解放タイマーを取り消して同じbankを使い、連打で音源を蓄積しません。
通常のメニュー停止ではPCMを再利用し、OFFではフェード後にPCMも解放します。
中断状態や最終disposeでは即時解放し、WebGL停止では共有contextも閉じます。

sourceはループ再生を担うだけで、過去の音符を予約するスケジューラーを持ちません。
開始時は現在のゲーム経過秒をループ長で割った位置を使います。
低fps・複数周期ジャンプは現在のミックスへ直接追従し、過去の音をまとめて鳴らしません。
AudioContextの時刻は発音とgainのフェードにだけ使用し、ゲーム環境の判定には使用しません。
アタリ音の発生条件・呼び出し位置は維持し、880→1320Hz・peak 0.12・0.32秒の通知を保ちます。
生成・再生の失敗は捕捉し、アワセや釣りの状態機械へ例外を伝播させません。

### PCMの音量の谷と生成負荷

再生開始の問題とは別に、修正前PCMの伴奏が6／12／18／24秒で同時にゼロへ近づくことを確認しました。
境界を中心とする100ms RMSは約0.000048（夜12秒は0.00000784）で、夜の旋律の休符中の
約0.012より大幅に小さい値でした。長い完全無音や継ぎ目の大きな段差は確認していません。
開始位相が境界付近の場合にも音量が小さくなるため、不規則な端末側の瞬断とは区別して評価します。

伴奏だけを同じ和音の中心位置のまま8秒へ広げ、両端を重ねました。各音の音量は
`sqrt(6/8)`倍でエネルギーを補正し、旋律・休符・音程・自然音は維持しています。
最終和音を先頭へ折り返し、10msの微小補正で継ぎ目のサンプル差をゼロにします。

| 生PCM・24秒 | 昼：修正前 → 後 | 夜：修正前 → 後 |
| --- | --- | --- |
| 全体RMS | 0.032191 → 0.031305 | 0.026681 → 0.026413 |
| 最小50ms RMS | 0.00000490 → 0.003940 | 0.00000454 → 0.002627 |
| RMS 0.001未満の連続窓（継ぎ目を含む） | 約0.450秒 → 0秒 | 約0.700秒 → 0秒 |
| peak | 0.095490 → 0.097954 | 0.095457 → 0.095050 |

50ms窓は1,103サンプル（約50.023ms）です。0.001は解析のしきい値で、可聴限界ではありません。
全体音量を上げる対応ではなく、両BGMの全体RMSはわずかに減少しています。
自然音PCMは修正前と同一、3本のPCMは引き続き合計6,350,400 bytesです。

初回の同期PCM生成はNode v24のクラウド環境で約121ms、続く3回は約109〜116msでした。
サンプルごとの三角関数評価を等価な回転漸化式に変更した後は、初回約52ms、続く3回は約32〜38msでした。
元の6秒構成で生成方式だけを置き換えた比較の最大サンプル差は7.45e-9です。
計測値は端末負荷で変動し、スマートフォンでの処理時間や音切れの主因を証明するものではありません。
初回生成負荷は軽減しますが、メニュー再開では既存PCMキャッシュをそのまま再利用します。

### gain出力の検証と修正

Chromium 154.0.8037.57のネイティブOfflineAudioContextで、一定値1のPCMを実際のplayerへ渡し、
30／60／144fpsと不規則な更新間隔で夜明けの16秒クロスフェードをレンダリングしました。
音楽的な休符を除いたこの条件でも、修正前の`cancelAndHoldAtTime`経路は期待する出力0.12から
一時的に0へ落ちるサンプルがありました。非対応時のフォールバックでは、初回やbank再生成時に
未描画の初期イベントをキャンセルした後、`AudioParam.value`の既定値1を採用して出力3になる現象も再現しました。
これは検証環境で確認した出力不連続であり、報告された端末の音切れ原因との一致は未確定です。

修正後は各gainの直前の開始値・目標・開始時刻だけを保持し、AudioContext時計から現在の線形値を求めます。
予約の置き換え時はその値を明示的に固定し、従来どおり80ms先へランプを予約します。
変化中の目標は更新ごとに追従しますが、`AudioParam.value`やholdの挙動には依存しません。
描画停止中も音声時計で予約済みランプが完了し、bank解放時は追跡情報も消去します。
昼夜16秒・濃霧前後12秒の目標ミックスと共有ゲーム時計は変更していません。

この修正時（常時自然音の追加前）の8条件（4更新間隔×holdの有無）は、クロスフェード出力0.119999886〜0.120000109、
最大隣接サンプル差0.000136未満（開始フェード）、停止完了後は厳密に0でした。
途中の停止・再開、PCM再利用、24秒の複数継ぎ目も検証し、同時sourceは最大3本、PCM生成は1回でした。
`tests/browser/audio-gain.spec.js`は数値JSONを保存し、既存のCI診断成果物にも含まれます。
OfflineAudioContextは実時間のCPU過負荷や出力機器を再現せず、この検証を聴取評価とは扱いません。

## 保存

音声設定はゲーム進行とは別の小規模なユーザー設定です。
専用キー`barb.audio.preferences.v1`へ次の3フィールドだけを保存します。

```json
{ "version": 1, "enabled": false, "volume": 40 }
```

バージョンは数値1、enabledはboolean、volumeは0〜100の整数のみを許可し、未知フィールドも拒否します。
入力長は256 UTF-16コード単位以内です。JSON破損・不正値・読み込み不能ではOFF／40%を採用します。
読み込みは書き込み・削除・修復をせず、明示的に設定値を変更した時だけ専用キーへ書き込みます。
書き込み失敗でも今回の設定で続け、音声設定の保存失敗を個別に表示します。次の変更で再試行できます。

ゲームの`saveVersion: 1`、`settings: {}`、2スロットの形式・世代・競合検出・保護・自動保存は変更しません。
音声設定をスロットへ混入させず、設定変更でゲームの保存成功や競合停止を発生させません。
他タブの音声設定を実行中セッションへ自動適用せず、再読み込み時に採用します。
ゲームの保存停止中も音声設定だけは独立して変更できます。

## 自動再生制限とライフサイクル

保存されたONでも、ページ読み込みだけではAudioContextを作成しません。
信頼されたユーザーイベント内で、画面が表示中であり、`navigator.userActivation`がある場合は
`isActive`も確認してから生成・`resume()`を同期的に呼びます。
マウスはpointerdown、タッチ等はpointerup、キーボードはkeydown、実際のclickを対象とします。
PointerEvent非対応時はtouchendを補完し、touchstartだけでは開始しません。
ON／再試行ボタンは自身のclickで開始を要求します。document側の先行ポインター処理で
再試行ボタンを消したり、同じボタンのclick要求を奪ったりしません。
初回操作はアタリ音も従来どおりアンロックし、環境音はONの場合だけ開始します。
非対応・生成失敗・resume拒否では無音で続行できます。

### 再生開始の調査と状態

修正前には、初回の`resume()`が未完了の間は次の要求にも同じPromiseを返す経路がありました。
これが保留し続けると、有効な再試行タップでも新しい`resume()`を呼べません。
また、タッチのpointerdownはブラウザの一時的なユーザー操作許可より早く届く可能性があります。
前者はコードと制御可能なFake AudioContextで確認する不具合、後者が報告された実機Chrome／Braveで
最初の保留を起こしたかは未確定の仮説です。実機のイベント履歴やOS・ブラウザ版は未確認です。

修正後は、前のPromiseが保留中でも、新しい有効なユーザー操作から同じcontextへ新しい`resume()`を呼びます。
各要求は世代番号と呼び出し時のcontextを持ち、古い解決／拒否で新しい状態を上書きしません。
Promiseの完了前にstatechangeでrunningになった場合も、その実状態を採用します。
closedからのcontext置換は次のユーザー操作時だけ、dispose後の結果は無視します。
毎フレームのresume、タイムアウトによる成功判定、自動的なcontext再生成は行いません。

| 状況 | 表示状態 | 再試行 |
| --- | --- | --- |
| ONだが操作前 | waiting「操作後に再生できます」 | 表示 |
| resume要求後、まだrunningではなく応答待ち | starting「音声を開始しています。応答がない場合は再試行できます」 | 表示・操作可能 |
| 現在の要求が拒否／再生経路が失敗 | blocked「開始できませんでした。再試行できます」 | 表示 |
| contextがsuspended／interrupted／closedへ変化 | interrupted「音声が中断されました。再試行できます」 | 表示 |
| runningだがメニュー等の停止理由がある | paused「一時停止中（メニューなど）」 | 非表示 |
| runningで停止理由がなく、音量が有効、playerの開始処理も成功 | playing「再生中」 | 非表示 |

メニュー停止中でも、まだアンロックできていなければ操作待ち／開始処理中／失敗の表示を優先します。
OFFは常にoff、音量0はアンロック後にmuted、Web Audio非対応はunsupportedです。
playingは端末のスピーカーから音が聞こえたことを証明する表示ではありません。

メニュー、非表示、フォーカス喪失、pagehideはそれぞれ独立した停止理由です。
全理由が解除されて初めて、現在の設定・共有時計で再開します。ページ復帰時の過去音の追い掛け再生はありません。
起動時のhasFocusがfalseのままfocusイベントが届かない状態と、明示的なwindow.blur後を区別します。
起動時は有効なマウスpointerdown／keydown、または新しいタッチの完了で復旧できます。
明示的なblur後のPC操作はwindow.focusを待ち、途中の操作から遅れて届くpointerup／clickや
新しいマウスclickだけではゲーム時計・blur停止理由を復旧しません。
モバイルでfocus通知が欠落する場合は、blur後に新しく始まったtrustedなタッチと、それに対応する
有効なpointerup（PointerEvent非対応時はtouchend）でのみ復旧できます。タッチ開始の記録は
blur／非表示／pagehide／pointercancel／touchcancelで破棄し、blur前の操作の末尾を採用しません。
復旧時はゲーム時計の前回時刻をリセットし、停止時間を加算しません。hidden／page／menu理由も残します。
音声のアンロック許可とゲームのフォーカス復旧は別に判定し、blur理由が残る間はrunningでも環境音を再生しません。
ロック・着信・アプリ切替等でcontextがsuspended／interruptedになった場合は音源を解放します。
focus／pageshowだけでは`resume()`せず、次のユーザー操作または「音声の開始を再試行」で再開します。
WebGL context喪失時は環境音と共有contextを解放し、既存の再読み込み案内に従います。
ブラウザが復帰を許可しない場合もゲームへ例外を流しません。

## 検証・聴取手順

```bash
npm ci
npm test
npm run build
npx playwright test tests/browser/audio.spec.js --reporter=line
npx playwright test tests/browser/audio-gain.spec.js --reporter=line
node scripts/render-audio-preview.mjs /tmp/barb-audio-preview
```

最後のコマンドは4モード、夕暮れ・夜明け・濃霧の開始・濃霧明け（各24秒）、
昼夜の2ループ（各48秒）のWAVと、50ms RMS等の`metrics.json`、固定スケールの`waveforms.svg`を生成します。
音源生成と純粋ミックスを用い、初期音量40%を適用しており、音量の正規化はしていません。
AudioParamの80ms追従やブラウザ／端末の出力特性までは再現しません。
生成物はコミットしません。実際のブラウザの確認には`npm run dev`を使います。

同じ解析・出力処理で修正前後を再生成できます。比較資料は正規化せず、40%の設定で出力します。

```bash
git show 43a2ba09b456966488ca8a2562847a80ed2b4554:src/audio/generated-sources.js > /tmp/barb-generated-before.mjs
node scripts/render-audio-preview.mjs /tmp/barb-audio-preview/before --source /tmp/barb-generated-before.mjs
node scripts/render-audio-preview.mjs /tmp/barb-audio-preview/after
```

全件E2EはGitHub Actionsで実行します。Codexは関連E2Eの局所結果と未実行項目をPRへ記録し、
CIの完了を待機・継続監視しません。詳細は[検証フロー](TESTING_WORKFLOW.md)を参照してください。

### 実機での再生・聴取確認

ユーザーによるマージ・デプロイ後、各ブラウザで次を実施してください。端末音量は小さめから始めます。

1. BARBを開き、端末OSとブラウザのバージョンを下表へ記録します。
2. 「≡」→「サウンド設定」でBGM・自然音をONにします。
3. ゲーム内音量を40%にします。端末の消音や出力先も確認します。
4. メニューを閉じます。
5. BGMが実際に聞こえるか確認します。状態を調べる場合はサウンド設定を再度開きます（メニュー中は一時停止します）。
6. 「音声の開始を再試行」が表示される場合はタップします。開始処理中のままでも、別のタップで再試行できます。
7. 操作前・ON後・再試行後の状態表示を記録します。再試行後に一時停止中へ変わった場合は、メニューを閉じて聴取します。
8. 別アプリ／タブや画面ロックへ移り、戻ります。中断表示がある場合はタップまたは再試行し、復帰後の聴取と状態を記録します。
9. ページを再読み込みします。ON／音量が復元され、実際の操作後に同様に開始・再試行できるか確認します。
10. メニューを閉じて24秒以上連続再生し、複数ループを聴きます。音切れがあれば発生時刻、開始直後か、6秒刻みか、継ぎ目かを記録します。
11. 昼夜の切り替え（境界前後8秒ずつ）を聴きます。通常霧の夜BGM、濃霧の前後12秒の自然音との移行も確認します。
12. 昼・通常夜・通常霧で自然音が控えめに継続し、BGMを妨げないか、濃霧ピークでBGMが消えて自然音が主体になるか比較します。

単体テストは境界、霧の強度、30/60/144fps、ジャンプ、厳格な設定検証、ストレージ障害、
ゲームセーブv1の往復互換、初回アンロック、拒否・中断、合成停止理由、発音の上限と解放、
アタリ音の音程・エンベロープ、PCMの有限値・peak・継ぎ目を検証します。
Playwrightは本番ビルドへテスト専用Web Audio観測を注入し、マウス／小型タッチ縦横、
メニュー・blur・hidden・pagehide・WebGL喪失、復元、拒否・中断、専用保存失敗を確認します。
ネイティブChromium AudioContextのテストと、pending／拒否を意図的に作るFakeのテストを分けます。
context生成、resumeの要求／完了、running、PCM生成、source作成／start、gainとdestinationへの接続を観測し、
イベント種類・userActivation・focus／visibility・UI表示もテスト資料に残します。
タッチエミュレーションでこの再生経路を確認できても、実機Chrome／Brave／LINEで聞こえることは別の確認です。
本番コードにはデバッグAPIや状態変更フックを公開しません。

自動テストやWAV生成は聴感品質の確認ではありません。実際の聴取評価、スマートフォン実機、
iOS Safari／WebKit、電話着信・画面ロックの実機確認は未実施です。
