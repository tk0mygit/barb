# BARB Codex恒久運用ルール

> 全てのCodexタスク、PMレビュー、および後続Phaseへ適用する。`AGENTS.md`の命令を具体化する補助正本。既存`docs/TESTING_WORKFLOW.md`のL0/L1/L2、CI、ユーザー承認を弱めない。

## R1 承認・工程・チャットを開始前に固定

- 指示書**本文外**に、展開するCodexチャット（新規/既存、同じPR修正は既存）、推奨モデル・思考レベル、基準main SHA、対象PR/Phase、理由を書く。
- 研究・設計・実装・CI修正・マージ・デプロイ・実機受入を別の権限として扱う。ユーザーPMが明示承認した範囲のみ実行する。古い工程の制限は、その工程に限定されたものか確認し、衝突があれば優先資料と衝突箇所を報告する。
- 研究の`本番編集禁止`を承認済み実装に誤って持ち越さない一方、実装承認を他Phase、mainへの直接push、マージ、部署外権限へ拡大しない。
- 作業開始時に実checkout HEAD、remote/main、作業ツリー、既存未コミット差分を確認し保護する。指定SHAが取得できなければ証拠を残して停止し、古いcheckoutを最新main扱いしない。

## R2 変更影響行列をPR実装前に作成

- ゲーム状態/確率/時計、入力アダプター、カメラ/描画、HUD/DOM、保存/売価、E2E撮影、比較器、CI集約器、CLI/ワークフローを行にし、直接変更と**間接的な観測差**を別々に記録する。
- FIGHTの距離を変えると、描画コードを変更しなくても追従カメラのクォータニオンが変わることを具体例として、撮影fixtureの前提を点検する。
- 関数・型・非同期契約を変えたら、同名/エイリアス呼び出し・テスト/レポート生成・最終集約まで**リポジトリ全体で参照を検索**し、末端CLIのプロセス終了コードまで確認する。

## R3 比較検証の厳格性を維持

- 比較値を、(a)必ず一致すべき不変条件、(b)承認された仕様変更で差が出る状態、(c)未解明の異常、の3種に分類する。意図されたゲーム状態変化を、カメラ等の無条件完全一致で誤判定しない。
- 特例は対象ID・対象ソースSHA・変更モジュール・正規化対象・復元に必要な入力列を明記した**最小範囲**に限る。実行時に両SHAのソースから独立再現し、同一追従/時刻履歴を与えたときの回帰を検査する。
- `cameraExpected`など添付済みの期待値を再検証の唯一の根拠にしない。撮影、比較、最終集約の全層でraw captureとsource provenanceを再検証する。
- 既存の他の比較ID、描画バッファ、解像度、リソース、HUD配置、画像収集、期待ID、収集/実行の整合を維持。assertionの削除・閾値緩和・skip・リトライ追加・固定sleep増加で見かけの成功を作らない。

## R4 CI最終ゲートを最初から設計・局所テスト

- PR作成前に、Unit/Build/Regular E2E/Mobile E2E/`ci-required`の各レイヤーに対して変更影響・必須証跡・成功条件を列挙する。`E2E PASS`を`ci-required PASS`と同一視しない。
- 撮影側比較関数を変えたら**最終ゲート側も同一契約**へ更新し、非同期ならすべての呼び出し元、`await`、拒否、サマリー、CLI `exitCode=1`まで透過させる。
- 集約検証は、実SHAに結びつく比較結果、34組/68画像等の規定対象、個別JSON、アーティファクトの署名/ハッシュ、検証用mergeの親SHA、全選択specと収集/実行IDを照合する。固定件数は当該仕様の根拠がある場合だけ保持し、勝手に減らさない。
- CI集約器変更は`AGENTS.md`・ワークフロー・CIテストと同様にL2。局所Unitには正常ケースと意図的な改竄/欠損/失敗を入れる。合成fixtureを実CIでのPASSと表示しない。

## R5 CI失敗を原因別に扱い、無駄な再実行を避ける

- 失敗場所を`unit / browser spec / afterAll比較 / ci-required集約 / Pages`のどこかに特定し、ジョブの成功/失敗と最終判定を分離する。
- CIログと失敗時artifactのJSON・screenshots・trace・SHAを収集し、発生したエラー、再現条件、根因、仮説、修正範囲、未検証範囲を報告。`Run failed`だけで推測修正しない。
- コードが決定論的に失敗する場合、同一HEADのall-jobs re-runを解決策としない。修正コミット→局所対象検証→新HEADでL2 CIが原則。
- CI待機・継続ポーリング・ローカル全件E2EをCodexの責務にしない。局所E2E・Unit/Build/静的チェックを先に行い、既存の選択・CI運用規則に従う。

## R6 レビュー・コスト・継続性

- PRは1責務・差分/依存/必要CIを明記。テスト用巨大fixture・非本番資産が増えた場合はサイズ/由来を確認し、検証に必要なものだけをコミット。
- PR本文に最新HEAD、mainと検証merge、変更対象、実行/未実行、テスト数、timeout・既知懸念、初回失敗の原因を併記。後続PASSを使って旧失敗の記録を消さない。
- PMは最新HEADの`ci-required`と検証mergeの親が現行main/PR HEADであることを確認。ユーザーPMだけがマージし、デプロイ成功と実機受入を別確認する。
- 新規PRごとに新規Codexチャット。同一PRのCI修正は既存チャット。長い研究/チャットでは短縮チェックポイントを作り、採用決定・未決・根拠・基準SHAを保存する。
